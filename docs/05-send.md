# 05. 메일 발송 (send)

**목적**: mailon.kr 웹메일의 쓰기(compose) 화면을 자동으로 채우고, **검증에 성공한 경우에만** 실제로 메일을 발송
**파일**: `mailon/send.py` + `mailon/send_trigger.py` + `mailon/send_verify.py` + `mailon/main.py`
**CLI**: `python -m mailon.main send --to <주소> --subject <제목> --body <본문> [--dry-run | --confirm-send]`

---

> **경고 — 실발송은 되돌릴 수 없습니다**
>
> - 한 번 나간 메일은 회수할 수 없습니다. 이 명령은 실제 계정으로 실제 수신자에게 메일을 보냅니다.
> - **항상 `--dry-run`으로 먼저 확인하십시오.** 드라이런은 쓰기 화면을 열어 필드를 채우기만 하고, 네트워크 POST가 한 건이라도 관측되면 즉시 실패합니다.
> - 실행 전 **수신자 주소를 눈으로 직접 확인**하십시오. 이름만 알고 주소가 확실하지 않다면 먼저 [06-resolve.md](06-resolve.md)로 주소를 확인하십시오.
> - `--confirm-send`는 귀찮은 절차가 아니라 **오발송을 막는 안전장치**입니다. 자동화 스크립트에서 이 플래그를 기본으로 붙여두는 습관은 안전장치를 무력화합니다.

---

## 1. 두 개의 모드와 안전 게이트

`send`는 두 가지 모드로만 동작합니다.

| 모드 | 플래그 | 동작 |
|---|---|---|
| 드라이런 | `--dry-run` | 로그인 → 쓰기 화면 열기 → 필드/본문 채우기까지만. 발송 트리거를 호출하지 않음 |
| 실발송 | `--confirm-send` | 위 전 과정 + 발송 트리거 + 발송 후 메일함 확인 |

두 플래그를 **모두 생략하면 명령은 아무 일도 하지 않고 종료 코드 1로 거부**됩니다 (`confirmation_required`). 로그인조차 시도하지 않습니다. 즉 "실수로 엔터를 눌러서 메일이 나가는" 경로가 존재하지 않습니다.

```
send 호출
  ├── --dry-run 도 --confirm-send 도 없음 → 즉시 거부 (exit 1), 브라우저 미기동
  ├── --dry-run                          → 폼 구성까지만 (exit 0)
  └── --confirm-send                     → 폼 구성 + 발송 + 검증
```

`--dry-run`과 `--confirm-send`를 동시에 준 경우 `--dry-run`이 우선합니다 (실발송하지 않음).

## 2. 플래그 레퍼런스

`mailon/main.py`의 `build_parser()` 정의 기준입니다.

| 플래그 | 필수 | 반복 | 기본값 | 설명 |
|---|---|---|---|---|
| `--to` | **필수** | 가능 | 없음 | 수신자 주소. 반복 지정 가능 |
| `--cc` | 선택 | 가능 | `[]` | 참조 주소. 반복 지정 가능 |
| `--subject` | **필수** | 불가 | 없음 | 제목. 공백만 있으면 거부됨 |
| `--body` | **필수** | 불가 | 없음 | 본문. 공백만 있으면 거부됨 |
| `--attachment` | 선택 | 가능 | `[]` | 첨부 파일 경로. §2.2의 제약을 반드시 확인 |
| `--dry-run` | 선택 | - | 꺼짐 | 발송하지 않고 폼 구성까지만 수행 |
| `--confirm-send` | 선택 | - | 꺼짐 | 실발송 승인. 없으면 실발송 경로가 열리지 않음 |
| `--json` | 선택 | - | 꺼짐 | 결과를 한 줄 JSON으로 출력. 로그는 표준에러로 분리 |

`--to`가 하나도 없으면 `argparse` 단계에서 거부되고, 값이 있어도 정규화 결과가 비면 `SendValidationError`가 발생합니다.

### 2.1 주소 입력 형식 (반복 플래그와 구분자 문자열 모두 허용)

`--to`, `--cc`는 `mailon/main.py`의 `_split_addresses()`가 정규화합니다. 세미콜론은 콤마로 치환한 뒤 콤마로 분리하고, 각 조각의 앞뒤 공백을 제거하며, 빈 조각은 버립니다. 따라서 아래 세 가지는 모두 동일하게 해석됩니다.

```bash
--to first@example.com --to second@example.org
--to "first@example.com, second@example.org"
--to "first@example.com; second@example.org"
```

반복 플래그와 구분자 문자열을 섞어 써도 됩니다. 사람이 손으로 입력하는 경우와, 다른 스크립트가 한 줄로 결합해 넘기는 경우를 모두 수용하기 위한 설계입니다.

### 2.2 첨부 파일의 현재 제약

`--attachment`는 CLI 인자로는 받지만, **실발송 경로에서는 아직 거부**됩니다. `mailon/send.py`는 드라이런이 아닌 상태에서 첨부가 하나라도 있으면 `SendSafetyError("attachment upload requires a verified file input")`을 발생시키고 종료 코드 2로 끝냅니다. 파일 입력 요소를 통한 업로드가 아직 검증되지 않았기 때문에, 첨부가 조용히 누락된 채 메일이 나가는 것보다 거부하는 쪽을 택한 것입니다.

드라이런에서는 첨부 개수만 결과의 `attachment_count`에 집계됩니다.

## 3. 종료 코드

| 코드 | 의미 | 발생 지점 |
|---|---|---|
| **0** | 성공 (드라이런 성공 포함) | 정상 종료 |
| **1** | `--dry-run`도 `--confirm-send`도 없이 호출 (안전 게이트). 또는 `.env` 설정 누락 등 구성 오류 | 실행 전 거부 |
| **2** | 로그인 실패, 브라우저 오류, `SendValidationError`, `SendSafetyError` | 실행 중 fail-closed |

종료 코드 2는 "무언가 확신할 수 없는 상태"를 뜻합니다. 특히 `SendSafetyError`는 **잘못된 메일이 조용히 나가는 대신 거부된 결과**이므로, 설계상 의도된 정상 동작입니다. 자세한 판별은 §6과 §10을 참고하십시오.

## 4. 사용 예시

### 4.1 권장 절차: 드라이런 → 확인 → 실발송

```bash
REM 1단계. 실제로 보내지 않고 폼이 제대로 구성되는지 확인
.venv\Scripts\python -m mailon.main send ^
  --to recipient@example.com ^
  --subject "회의록 공유" ^
  --body "안녕하세요. 회의록을 공유드립니다." ^
  --dry-run
```

출력 예:

```
OK: dry_run; POST=0
```

로그에 남은 폼 상태(`compose form state: ...`)에서 수신자와 본문이 의도대로 들어갔는지 확인합니다.

```bash
REM 2단계. 수신자 주소를 눈으로 다시 확인한 뒤에만 실발송
.venv\Scripts\python -m mailon.main send ^
  --to recipient@example.com ^
  --subject "회의록 공유" ^
  --body "안녕하세요. 회의록을 공유드립니다." ^
  --confirm-send
```

출력 예:

```
OK: submitted; POST=1
```

### 4.2 다중 수신자와 참조

```bash
.venv\Scripts\python -m mailon.main send ^
  --to first@example.com --to second@example.org ^
  --cc "manager@example.com, archive@example.org" ^
  --subject "월간 보고" ^
  --body "월간 보고 초안을 첨부 없이 본문으로 보냅니다." ^
  --dry-run
```

### 4.3 JSON 출력 (다른 프로그램에서 호출할 때)

```bash
.venv\Scripts\python -m mailon.main send ^
  --to recipient@example.com ^
  --subject "자동 알림" ^
  --body "정기 점검이 완료되었습니다." ^
  --dry-run --json
```

```json
{"attachment_count":0,"csrf_present":true,"network_post_count":0,"status":"dry_run","verified":false}
```

`--json`을 주면 로그 스트림이 표준에러로 옮겨가므로 **표준출력은 JSON 한 줄만** 나옵니다. 파싱하는 쪽에서 로그와 섞일 걱정이 없습니다.

## 5. 출력 형식

### 5.1 성공

| 모드 | 표준출력 |
|---|---|
| 기본 | `OK: <status>; POST=<네트워크 POST 수>` |
| `--json` | `SendResult`의 JSON 직렬화 (키 정렬, 공백 없음) |

`SendResult` 필드:

| 필드 | 의미 |
|---|---|
| `status` | `dry_run` 또는 `submitted` |
| `csrf_present` | 쓰기 화면에서 발송용 CSRF 토큰을 확인했는지 |
| `attachment_count` | 요청에 포함된 첨부 개수 (실발송 경로는 항상 0) |
| `network_post_count` | 관측된 POST 요청 수 |
| `verified` | 발송 후 메일함 확인까지 통과했는지 |

### 5.2 실패

| 모드 | 출력 |
|---|---|
| 기본 | 표준에러에 `FAIL: <error_code>` |
| `--json` | 표준출력에 `{"status":"error","error_code":"<error_code>"}` |

`error_code`로 올 수 있는 값은 다음과 같습니다.

| `error_code` | 종료 코드 | 의미 |
|---|---|---|
| `confirmation_required` | 1 | `--dry-run`도 `--confirm-send`도 없음 |
| `LoginError` | 2 | 로그인 실패 (ID/비밀번호/OTP 또는 로그인 화면 변경) |
| `BrowserError` | 2 | `agent-browser` 호출 실패 |
| `SendValidationError` | 2 | 수신자 없음, 제목 없음, 본문 없음 |
| `SendSafetyError` | 2 | 안전 검증 실패로 발송 거부 또는 발송 후 확인 실패 |

오류 메시지 본문에 수신자나 본문이 그대로 실려 나가지 않도록 표준출력에는 **오류 종류만** 출력합니다. 상세 진단은 `logs/sync-YYYY-MM-DD.log`에 남습니다.

## 6. 실행 파이프라인

`--confirm-send` 경로의 전체 순서입니다.

```
1. 인자 검증        --to/--subject/--body 정규화, SendRequest 생성
2. 로그인           ID + 비밀번호 + TOTP (전용 세션)
3. 중복 억제 사전점검 최근 20분 내 동일 제목 + 동일 수신자 메일이 이미 있으면
                    재발송하지 않고 성공으로 종료
4. 쓰기 화면 열기    window._tbar.compose() 후 3초 대기
5. CSRF 확인        #sendCSRFToken 없으면 거부
6. 필드 채우기       수신자/참조/제목 + 본문(에디터 프레임)
7. 수신자 토큰화     한 명씩 Enter로 입력해 chip 등록
8. 폼 게이트         _compose.getForm()의 실제 발신 파라미터 검증
                    → 본문 누락 시 에디터 API로 재주입 후 재검증
                    → 그래도 불일치면 발송 거부 (exit 2)
9. 발송 트리거       _compose.send() → 실패 시 보내기 버튼 클릭 폴백
                    → 둘 다 불가하면 발송 거부 (exit 2)
10. 1차 검증(빠름)   새 POST의 상태 코드 확인 (약 10초)
11. 2차 검증(확정)   보낸 메일이 메일함에 나타나는지 폴링 (약 45초)
12. 기록            logs/send-attempts.jsonl에 결과 한 줄 추가
```

드라이런은 6번까지만 수행하고, 이 단계에서 POST가 한 건이라도 관측되면 `SendSafetyError`로 실패합니다. "드라이런인데 실제로 무언가 전송되었다"는 상황 자체를 오류로 취급합니다.

## 7. fail-closed 설계 — 각 장치가 존재하는 이유

아래 항목들은 모두 **실제 오발송·미발송 사고를 겪고 나서 추가된 방어 장치**입니다. 코드가 복잡해 보인다는 이유로 걷어내면 같은 사고가 반복됩니다.

### 7.1 `beforeSend()`만 호출하면 메일은 나가지 않는다

`window._compose.beforeSend()`는 이름 그대로 **발송 직전에 실행되는 사전 훅**일 뿐, 그 자체가 발송이 아닙니다. 이 함수만 호출하는 구현은 아무 예외도 내지 않고 성공한 것처럼 보였지만, 자가 시험 메일은 끝내 도착하지 않았고 동기화된 수백 통의 메일에서도 흔적이 없었습니다.

그래서 지금은 **사람이 하는 것과 동일한 경로**를 탑니다. 즉 검증 → `beforeSend` → 실제 제출로 이어지는 핸들러 체인 전체를 실행합니다. 구현은 쓰기 화면이 최종적으로 호출하는 실제 진입점(`_compose.send()`)을 우선 사용하고, 그것을 쓸 수 없으면 **쓰기 폼의 보내기 버튼을 실제로 클릭**하는 폴백을 사용합니다. 버튼 탐색은 발송 폼 범위 안에서 먼저 찾고, 문서 전체 탐색은 후보가 정확히 하나일 때만 인정합니다. 예약/임시저장/취소/전달 같은 라벨은 애초에 후보에서 제외됩니다.

둘 다 불가능하면 **아무것도 누르지 않고 거부**합니다. 어떤 버튼인지 확신하지 못한 채 클릭하는 것보다 실패하는 편이 안전하기 때문입니다.

### 7.2 자동화 환경에서 웹에디터 엔진이 죽는 문제

쓰기 화면의 본문은 웹에디터가 관리하며, `_compose.getForm()`은 발신 본문을 `mail_editor.getContent()`에서 읽어갑니다. 그런데 자동화 브라우저에서는 에디터 엔진이 정상 기동하지 못하는 경우가 있고, 이때 `setContent()`는 아무 일도 하지 않으며 `getContent()`는 `undefined` 또는 빈 문자열을 돌려줍니다. 즉 **본문이 `undefined`인 채로 메일이 나갈 수 있는 상태**가 됩니다.

방어 순서는 다음과 같습니다.

1. 에디터 프레임 본문에 값을 쓰고 `input` 이벤트를 발생시킨다.
2. 폼 게이트가 본문 누락을 감지하면 에디터 API(`setContent`)로 다시 주입한다.
3. 주입 직후 `getContent()`를 **되읽어 검증**한다.
4. 되읽은 값이 비었거나 `undefined`를 포함하면, `getForm()`이 실제로 참조하는 접근자인 `getContent` 자체를 덮어써서 **결정론적으로 본문을 반환**하게 만든다.
5. 그래도 폼에서 본문을 확인할 수 없으면 발송을 거부한다.

### 7.3 수신자는 한 명씩 Enter로 토큰화해서 입력한다

수신자 입력란은 단순 텍스트 필드가 아니라 주소를 chip(토큰)으로 등록하는 위젯입니다. 여러 주소를 콤마로 이어 붙여 한 번에 넣으면 **chip이 하나도 등록되지 않고**, 결과적으로 `getForm()`이 수신자 0명을 들고 있게 되어 폼 게이트에서 거부됩니다.

그래서 `#adr-to-ipt_ta`(수신)와 `#adr-cc-ipt_ta`(참조)에 주소를 **한 명씩 넣고 매번 Enter 키 이벤트로 토큰화**합니다. 값 주입은 네이티브 setter를 통해 수행해 위젯 내부 모델이 변경을 인지하도록 합니다.

### 7.4 발송 직전 실제 발신 파라미터를 검증한다

발송 트리거를 호출하기 전에 `_compose.getForm()`을 호출해 **실제로 서버에 나갈 파라미터**를 확인합니다.

- 본문: 본문의 첫 유효 줄 앞부분을 표식으로 삼아, 폼 파라미터 어딘가에 그대로 들어 있는지 확인
- 수신자: 요청한 모든 주소가 폼에 들어 있는지 확인
- 자기 자신에게 보내는 모드(`method=tome`)로 폼이 재작성된 경우에는, 요청한 수신자가 전부 발신 주소와 일치할 때만 인정

하나라도 어긋나면 **발송을 거부하고 종료 코드 2로 끝냅니다.** 이때 폼 상태는 로그에 남습니다. 이 게이트가 동작해 rc=2로 실패한 것은 고장이 아니라, **내용이 깨진 메일이 조용히 발송되는 사고를 막아낸 것**입니다.

### 7.5 발송 후 검증은 ANY-recipient 매칭으로 한다

발송 성공 여부는 두 층으로 확인합니다.

- **1층(빠른 실패)**: 발송 트리거 직전의 요청 목록을 기준선으로 잡고, 이후 새로 생긴 POST만 봅니다. 4xx/5xx가 보이면 즉시 실패. 새 POST가 하나도 없으면 "아무것도 보내지지 않았다"로 판정해 실패. 상태 코드가 창 안에 관측되지 않은 경우는 도구 버전 차이일 수 있으므로 2층으로 판단을 넘깁니다.
- **2층(확정)**: 메일 목록 API를 폴링해, 보낸 메일이 메일함에 나타나는지 확인합니다. 조건은 **정확한 제목 일치 + 시간창(발송 시각 기준, 시계 오차 120초 허용) + 수신자 ANY 매칭**입니다.

여기서 ANY 매칭이 핵심입니다. 목록 화면은 다중 수신자 메일의 **첫 번째 수신자만** 표시합니다. 모든 수신자가 다 보여야 성공으로 치는 ALL 매칭을 쓰면, 정상적으로 발송된 메일을 실패로 오판하고 **재시도 루프에 빠져 같은 메일을 반복 발송**하게 됩니다.

### 7.6 중복 발송 억제

검증이 거짓 음성으로 실패한 뒤 사람이나 스크립트가 재시도하는 상황을 대비해, 실발송 직전에 **최근 20분 이내에 동일 제목 + 동일 수신자 메일이 이미 메일함에 있는지** 먼저 확인합니다. 있으면 다시 보내지 않고, 이미 전달된 것으로 간주해 성공(`verified=true`, `network_post_count=0`)으로 종료합니다.

### 7.7 발송은 sync와 분리된 전용 브라우저 세션에서 실행된다

발송은 `mailon-sync-send`처럼 기본 세션 이름에 `-send` 접미사를 붙인 **별도 브라우저 세션**을 사용합니다. 세션을 공유하면 발송이 쓰기 화면으로 이동하는 순간 **동시에 돌고 있던 동기화 작업이 죽습니다.** `resolve` 역시 같은 이유로 `-resolve` 접미사의 자체 세션을 씁니다.

### 7.8 시도 기록

성공적으로 끝난 시도(드라이런 포함)는 `logs/send-attempts.jsonl`에 **한 줄 JSON**으로 누적됩니다.

```json
{"attachment_count":0,"csrf_present":true,"network_post_count":1,"status":"submitted","verified":true}
```

이 파일에는 수신자 주소, 제목, 본문이 기록되지 않습니다. 다만 `logs/`는 전체가 gitignore 대상이며, 진단 로그에는 폼 상태가 남을 수 있으므로 [07-security.md](07-security.md)의 로그 위생 규칙을 따르십시오.

## 9. 알려진 취약점과 한계

- **웹메일 내부 구조에 강하게 결합**되어 있습니다. `window._compose`, `window.mail_editor`, `#adr-to-ipt_ta`, `#adr-cc-ipt_ta`, `#compose_subject`, `#sendCSRFToken`, 에디터 프레임 식별자 등은 모두 서비스 내부 구현입니다. 사이트가 개편되면 이 경로는 깨집니다. 다만 깨질 때는 **조용히 잘못 보내는 대신 종료 코드 2로 거부**되도록 설계되어 있습니다.
- **브라우저 안에서 실행되는 JS 부분은 오프라인 테스트로 덮이지 않습니다.** 에디터 접근자 덮어쓰기나 버튼 탐색 같은 인브라우저 로직은 실제 화면 없이는 검증할 수 없습니다. 주소 정규화, 수신자 토큰화 호출, ANY-recipient 매칭, 폼 게이트의 실패 처리 등 파이썬 쪽 로직은 `tests/test_offline.py`가 덮고 있습니다.
- **첨부 업로드 미지원** (§2.2).
- 자기 자신에게 보내는 경우 폼이 `tome` 모드로 재작성될 수 있으며, 이때는 수신자 검증 방식이 달라집니다 (§7.4).

## 10. 문제 해결

| 증상 | 확인 순서 |
|---|---|
| `FAIL: confirmation_required` | 안전 게이트입니다. 의도한 발송이 맞다면 `--dry-run`으로 먼저 확인한 뒤 `--confirm-send`를 붙이십시오 |
| `FAIL: SendValidationError` | `--to`/`--subject`/`--body` 중 비었거나 공백뿐인 값이 없는지 확인 |
| `FAIL: LoginError` | [01-login.md](01-login.md)의 진단 절차. 시각 동기화와 TOTP 유효 시간을 먼저 확인 |
| `FAIL: BrowserError` | `agent-browser doctor --offline --quick`, 좀비 세션 정리 |
| `FAIL: SendSafetyError`, 로그에 `compose form missing body/recipients` | 폼 게이트가 막은 것입니다. 로그의 폼 덤프에서 본문/수신자가 어떻게 들어갔는지 확인 (§7.2, §7.3) |
| `FAIL: SendSafetyError`, 로그에 `no send POST observed` | 트리거는 눌렸지만 전송 요청이 없었습니다. 실제로 발송되지 않았을 가능성이 높습니다 |
| `FAIL: SendSafetyError`, 로그에 `send not confirmed in mailbox` | 발송 요청은 나갔으나 메일함에서 확인하지 못했습니다. **재시도 전에 반드시 보낸 메일함을 직접 확인**하십시오. 이미 발송되었다면 중복 억제 창(20분) 덕분에 재시도해도 중복 발송되지 않습니다 |
| `FAIL: SendSafetyError`, 첨부 지정 시 | 첨부 업로드는 아직 지원되지 않습니다 (§2.2) |

로그 위치는 `logs/sync-YYYY-MM-DD.log`이며, 시도 요약은 `logs/send-attempts.jsonl`입니다.
